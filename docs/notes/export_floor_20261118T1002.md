# The ~21 s export floor, run 20261118T1002

Written 2026-11-19. Inputs: `views_timing_2026-05-05.csv` (1,955 rows) and
`export_fields.csv` (3,234 rows) from run `20261118T1002`, as supplied by Greg.
The run folder itself was not available. Every claim is labelled **OBSERVED**
(read from one of those two files, columns named) or **INFERENCE**. The numbers
below can be reproduced with:

```bash
python tools/analyze_export_floor.py views_timing_2026-05-05.csv
```

## Answer

**The stall follows a clock, not a view.** Whether an export is slow is
predicted by one number, the time since the previous stall. Run that through a
single threshold and it classifies **96.0 %** of the run's 2,569 exports
correctly. The threshold is ~28 s after the previous stall *ended*, or ~51 s
after it *started*. (OBSERVED, `tools/analyze_export_floor.py` over the timing
CSV.) An export that starts within 20 s of a stall ending is slow 1 % of the
time. One that starts more than 32 s after is slow 97 % of the time. The size of
the stall is tight: median **21.05 s** above the fast baseline for the export's
size (model exports, 5–95 %: 20.8–23.9 s).

INFERENCE: 21 s is the Windows default TCP connect timeout (initial
retransmission timeout 3 s, two retries: 3 + 6 + 12 = 21 s). The reading that
best fits a fixed 21 s stall which recurs ~30 s after it clears is this:
something on the export path **connects to an unreachable network endpoint**,
waits the full connect timeout, and caches the failure for ~30 s. Every export
inside that window is fast. The first export after the cache expires pays the
21 s again. This is neither hypothesis (a) nor (b) from the brief. It is (c).
The candidates and the test that decides between them are in "The A/B" below.

What it is NOT (OBSERVED):

- not the view. The same view state stalls or not depending on the clock:
  among annotation exports whose own view's model export was fast, the slow
  share is 0 % at 10–20 s since the last stall and 99 % at 30–45 s;
- not pixel count, beyond making views longer (below);
- not the output folder: the sidecar writes go to the same run folder within
  the same seconds and never exceed 0.6 s (`phase_sidecar_write_model_ms`
  max 522 ms, `phase_sidecar_write_annotation_ms` max 81 ms). No phase other
  than the two exports ever takes 18–35 s, except 13 `phase_suppression_ms`
  values on site plans, and those are real work: suppression tracks
  `phase_model_paint_ms` at r = 0.99.

What it costs (OBSERVED): 825 stalls, **4.9 h** of the 13.2 h capture time
(the slow export's duration less the linear fast baseline at its size).
INFERENCE: while exports run continuously, a 21 s stall every ~57 s is ~37 %
of wall time, *whatever else is made faster*. Colour mode is ~1 % of capture
time and does not touch this.

How the clock was found (OBSERVED; method in `tools/analyze_export_floor.py`):
the rows are in capture order. `mem_view_start_page_faults` and
`mem_view_start_gc2` rise monotonically down the 1,330 captured rows. Each
export's start time is rebuilt from the loop, pipeline and phase laps. The
model export's error is the capture's `unaccounted` (median ~0.6 s). The
annotation export is placed halfway through its pass's non-export time, which
can be off by a few seconds.

| time since previous stall ended | exports | slow |
|---|---|---|
| 0–20 s | 1,154 | 1 % |
| 20–24 s | 272 | 0 % |
| 24–28 s | 315 | 13 % |
| 28–30 s | 125 | 75 % |
| 30–60 s | 674 | 97 % |
| > 60 s | 28 | 96 % |

The clock's anchor (end vs start of the stall) is not settled. After the 81
stalls of 28 s or more, the since-end threshold moves earlier (~24 s) and the
since-start one later (~55 s). That suggests the timer starts *inside* the
stall, e.g. when the 21 s connect gives up, and the rest of a long slow export
is real work. The samples are small; the split timer (Part A) settles it.

## Step 1: the 33 duplicated view/pass pairs

**An extract bug.** They are not stale sidecars or recaptures. OBSERVED: every
duplicated file is one with `co_sizing_state` `applies`. The 12 files with
5 rows are two-attempt co-sized captures, and the 2 files with 3 rows are
confirmed seeds. Only the first row of each has `fit_direction` and
`view_scale`. The others match `stage_a_registered_capture._frame_summary`'s
key set exactly (`pixel_size`, `actual_w`, `actual_h`, `dim_check`,
`cap_applied`, `co_sized_fit_px`, `dim_check_attempts`).

The extract walked the whole JSON for anything frame-shaped. It therefore also
emitted `registration_marks.co_sizing.{first,second,seeded}_attempt.
{model,annotation}_frame`, one model and one annotation summary per attempt,
both labelled with the file's pass. Because both sidecars carry
`registration_marks`, an `_anno.json` produced model rows labelled `anno`. The
14 files cover 7 views (6 "P_RCP_TYPICALS - LEVEL n" plus "_N_ LOWER LEVEL -
Plumbing Study DH"), which accounts for 7 views × 2 passes × 2 or 4 extra rows
= 52 surplus rows. Taking only the top-level frame
(`stage_a_sidecar_shapes.frame_record`) leaves 3,182 rows with no duplicates.
That is the fix.

Added keys, all telemetry. No captured output changes, and
`TIMING_PARTITION` is untouched (`tests/test_stage_a_timing_subkeys.py`

`registration_marks.timings_ms`, both sidecars, so also `views_timing` as

| key | what |
|---|---|

The last two exist for the clock: with them, the next run's timeline needs no

## Step 4: the A/B

`tests/dynamo/probe_export_floor.py`, two views, no transaction, no change to
the document. It uses production `_export_tiff`. For each staging arm
(`temp` = production's `%TEMP%`, `run_folder` = a staging directory under the
probe's own folder) and each view: one first export, then repeats after idle
gaps of 0, 0, 5, 10, 20, 25, 30, 35, 45 and 60 s, each measured from the end
of the previous export. Optionally (default on) a separate PowerShell process
logs TCP connections in `SYN_SENT` every 0.5 s, with owning process, remote
address and port.

Readings (`verdict()`, tested offline in `tests/test_probe_export_floor.py`):

| reading | first export | repeat ≤ 10 s after a stall | repeat ≥ 35 s after | arms |
|---|---|---|---|---|
| (a) first export of the view after a change | slow | fast | fast | same |
| (b) every new file scanned | slow | slow | slow | same, or differ if the scan is path-scoped |
| (c) a clock | slow if the clock expired | fast | slow | same |

Also read from the record:

- `stall_part`, the export part that holds the slow exports' median: is the
  21 s inside `ExportImage`, or in `move` / `read_dims` (a scan on open)?
- `net_watch.syn_sent`: which process waits on which address during the
  stall. Under (c) this should be the smoking gun: Revit.exe or spoolsv.exe
  holding a `SYN_SENT` to one address for ~21 s, recurring every ~50 s.

and whether the machine's default printer is a network printer that is

## Step 5: what each result points to

- **(c), stall in `export_image`, a `SYN_SENT` from Revit.exe or
  spoolsv.exe.** INFERENCE, ranked:
  1. the default Windows printer is a network printer that cannot be
     reached. Revit's export and print paths query it, and an unreachable
     default printer stalls Revit's print/export dialogs. Fix: set a local
     default printer (e.g. Microsoft Print to PDF) for the capture session.
     That is a machine setting, not a code change;
  2. a network path the document or its links resolve on export (Desktop
     Connector, a UNC link path);
  3. licensing or telemetry.

  The address in `net_watch` names which. In all three, the fix is
  environmental and recovers ~37 % of export-heavy wall time.
- **(c), stall in `move` or `read_dims`.** An on-access scan with a cloud
  lookup that times out and caches the verdict. Stage under a scan-excluded
  path, or get `%TEMP%` (or the probe's `run_folder` arm, if it is fast)
  excluded. Do not change production's staging location before the arms
  differ.
- **(a).** Reorder so one export per view absorbs the penalty, or test
  whether a 1 px warm-up export moves it rather than adds to it. Run the
  probe with a 1 px first export: a warm-up that moves the penalty shows a
  slow 1 px export followed by a fast real one.
- **(b).** Stage under a scan-excluded path.
- **Nothing reproduces in the probe**, while the next production run's split
  timer still shows the stall. Then it needs Revit state the probe does not
  create (a committed change), and the next step is the same probe with one
  transaction committed between repeats.

## Step 6: `link_instances`, `suppress_commit`, `restore_commit`

**`model_graphics_state.link_instances`** (0.32 h over 1,239 model passes).
It reads, per view: `FilteredElementCollector(doc, view.Id).OfClass(
RevitLinkInstance)`, then per link `_gs_element_ref` (name, type),
`view.GetElementOverrides(link).Halftone` and
`view.GetLinkOverrides(link).Halftone` (`color_id_buffer.py`,
`_read_link_instances`). OBSERVED: median 308 ms, minimum 153 ms, p90 2.6 s,
max 13.3 s. 24 % of views exceed 1 s, and those hold 0.23 h of the 0.32 h. It
tracks `pipeline_signature_ms` at **r = 0.95**, the pipeline's own
view-scoped collector over the view's membership, and tracks link-count
proxies far less (`model_expand.expand_elements.linked` r = 0.53,
`model_link_proxies` r ≈ 0). INFERENCE: the cost is the **view-scoped
collector**, which evaluates the view's visibility over its whole content,
and not the per-link reads. It is paid again because the marks transaction
has changed the document since the signature's collector ran. A cheaper read
would take the link instances from the document-wide class filter and test
view visibility only for those few. No change made here. The element count
of the view (membership size) would confirm it, and it is not in either file.
The membership counts the capture reads (`record["membership"]`) are not
persisted for a two-pass capture, so the extract now writes two proxies from
what the model sidecar already carries: `near_face_w_count` (painted host
elements) and `link_instance_count` (the graphics state's link list). Rerun
the extract to test "collector, not links" without a new capture.

**`model_suppress_commit`** (0.60 h). It scales with **element count, not
pixels or type**: r = 0.90 with `model_paint_ms` (one override per painted
element), 0.88 with `model_link_filters`, 0.25 with pixel count. Medians by
pixel quartile are 1.3, 1.4, 1.5 and 1.9 s; by type, 1.3 s (elevations) to
1.6 s (plans).

**`model_restore_commit`** (0.50 h). Scales with **neither**: r = 0.10 with
pixels, 0.18 with paint. Median 1.42 s, p99 2.2 s.

INFERENCE on both: every committed transaction has a fixed **~1.16 s floor**
(OBSERVED minimums: `suppress_commit` 1.160 s, `restore_commit` 1.162 s;
medians: `marks_create` 1.41 s, `template_detach` 1.18 s where a template is
detached, 0 on the 229 views without one). That is about five fixed commits
per view, 5–7 s, and Revit's regeneration on commit is the likely floor.
`restore_commit` is the cheapest to remove, because the attempt's rollback
undoes the same writes (R1 already defers the members' restore). That is a
change for another PR. Both medians fell after the first two fifths of the run
(`restore_commit` 1.52 → 1.34 s, `suppress_commit` 1.80 → 1.36 s). That is
OBSERVED, and unexplained.
