## 2. Part A — why the ticks are not rendered

### A.1 What "painted" and "readback" prove

`vop_interwoven/stage_a_registration.py`, `create_registration_marks()` (line 1011):

- Each tick is a detail line made by `doc.Create.NewDetailCurve(view, Line…)` (line
  1070), in world coordinates computed from view UV through the view's own
  `Origin` / `RightDirection` / `UpDirection` (`_world`, line 1059).
- **readback** (lines 1116–1124): `curve.GeometryCurve.GetEndPoint(i)` for the
  created element, projected back through `view_basis.transform_to_view_uv`,
  compared to the requested `uv0` / `uv1`. It proves the element exists in the
  document with the requested geometry. It reads nothing about the view's
  rendering: not the crop shape, not visibility, not the export.
- **painted** (lines 1127–1128): `view.SetElementOverrides(id, paint)` did not
  raise. It proves an override was set, not that a pixel was drawn.

OBSERVED (06-21 `_3939979.json`, `registration_marks.marks[*]`): all 12 have
`painted: true`, `line_style_applied: true`, `readback_max_deviation_ft: 0.0`.
OBSERVED (06-21 `_3939979.tiff` and `_3939979_anno.tiff`): 0 pixels of
[139, 251, 11] and 0 pixels within L1 < 60 of it. Both facts are true at once: the
element existed; nothing of it reached the image.

### A.2 How `line_style.hidden` is computed

`_thinnest_line_style()` (line 754) iterates `curve.GetLineStyleIds()`, skips
non-solid styles (`_style_pattern_is_solid`, line 857), then asks
`_style_subcategory_hidden(view, style)` (line 869), which is exactly
`view.GetCategoryHidden(style.GraphicsStyleCategory.Id)`. The parent category is
read the same way, `_lines_category_hidden()` (line 741).

So `hidden` sees a Lines **subcategory hidden in V/G** (category or subcategory
visibility checkbox), on the view as it is at capture time (the template is detached
first, `view_template_detach.detached_on: "view"`). It does **not** see a **view
filter**: nothing in `vop_interwoven/` reads `View.GetFilters()`,
`GetFilterVisibility()` or `GetFilterOverrides()` for the view's own filters. The
only filter code is the link-category filters the capture itself creates
(`color_id_buffer.py` `_apply_link_category_filters`, line 1121). A template-applied
filter that hides Lines or a line style would survive the detach and be invisible to
this check. That is a real blind spot (H1), but it is not what happened to 3939979
(§A.4: the same template and style registered on 06-13).

OBSERVED (both runs, `registration_marks.line_style`): `path: visible_existing`,
`id 32262 "1-Solid-Red"`, weight 1, `hidden: [(Origin Mark) 32448]` only,
`subcategory_hidden_in_view: false`; `lines_unhidden.state: not_needed`,
`lines_category_hidden_before: false`. Identical in the two runs.

### A.3 Pass-level operations that touch detail lines

- **Model pass** hides the view's OTHER detail lines (`detail_line_ids`, line 627:
  annotation members in OST_Lines). The ticks are created after membership is read
  (`create_registration_marks` is called with the layout, the membership having
  been collected before), so they are never in that set. OBSERVED: `model_lines_visible:
  true` in `_3939979.json`.
- **Annotation pass** suppresses MODEL members with white overrides and white link
  filters (`white_membership_suppression`, line 498). The ticks are view-owned, so
  they are annotation members and are painted MARK_COLOUR in both passes
  (`colour_mode: shared`, OBSERVED in both sidecars).
- `must_be_subtracted: true` (OBSERVED, `registration_marks`) is a flag for the
  decoder to remove tick pixels; it hides nothing.
- Halftone, display style (`FlatColors`, OBSERVED), smooth edges (off, OBSERVED),
  underlay and view range: none is written for Lines by either pass; detail lines
  are not subject to view range or underlay in Revit, and none of these would
  explain a difference between 06-13 and 06-21 where every recorded graphics field
  is identical (§A.4).
- **Crop shape is never read.** `stage_a_registered_capture.split_crop_state()`
  (line 118) reads only `NumberOfSplitRegions` and the split flags of
  `GetCropRegionShapeManager()`. No code under `vop_interwoven/` reads
  `GetCropShape()`, `ShapeSet` or `RemoveCropRegionShape` (grep, HEAD). Crop A is
  `View.CropBox`'s 8 corners projected to UV and bounded
  (`view_basis.xy_bounds_from_crop_box_all_corners`, line 342, via
  `color_id_buffer.read_crop_uv`, line 3246, via `resolve_crop_a`, line 3389,
  `source: authored_read`, never written for an active authored crop).
- **The export** is `ExportRange.SetOfViews` + `ZoomFitType.FitToPage` +

**(a) Read and record the crop shape; fault, do not guess.** Smallest change; makes

```diff
@@ vop_interwoven/stage_a_registered_capture.py @@ def split_crop_state(view):
+def crop_shape_state(view, basis):
+    """The crop region's shape, as read: ``None`` when the view has no
+    shape manager, else the loops in view UV and whether the shape is the
```

`_is_axis_aligned_rectangle(loop, crop_uv)` is PURE: four vertices, each within
`CROP_READ_BACK_TOLERANCE_PX * fpp` of a corner of `crop_uv`. A rotated loop fails
it. The fault is reported and flagged (Greg, 2026-10-01: an unmeasured frame is
reported, not refused), and `tools/stage_a_grid.py` can read `crop_shape.loops`
the way it reads `split_crop.bands_uv` (line 360) to keep only cells inside the
polygon. Needs a test on a fixture loop at 12.91° (the 06-21 numbers) and on an
axis-aligned loop; no Revit run is needed to prove the predicate.

**(b) Un-shape the crop for the capture, inside the group.** The Q7 move:
`m.RemoveCropRegionShape()` in its own Transaction after the shape is recorded,
rolled back with the group; the export then renders crop A in full, the ticks are
inside it, the capture registers, and the analysis masks to the recorded polygon.
This is the fix that makes these views register. It must be probed first on the
06-21 archive (D, 2026-10-01: a crop write that reads back identical changed 8.8 %

between the shaped and un-shaped exports. If they are, (b) is a dozen lines beside
`remove_split_for_capture()` (line 156) and reuses its record/fault shape.

**(c) Place the ticks inside the polygon.** `relocate_marks_clear_of()` (line 282)
already moves ticks within their corner band; it takes rectangles to avoid, not a
polygon to stay inside. Extending it to "stay inside loop 0" keeps the authored
export exactly as it is, but a rotated rectangle inscribed in its bounding box
leaves no room near three of the four box corners (the tangent points), so the
corner ticks would move far along their band and the locator's thirds could
misassign them. Not recommended before (a) and (b).
