## 1. What the tool reads, and the definitions

All OBSERVED in `tools/stage_a_element_census.py` unless marked.

| figure | source |
|---|---|
| measured view | a requested view whose `stage_a_grid_rollup` row is `gridded` (the roll-up's `run_rows`, imported) |
| unmeasured view | any other requested view, by row status: `not_this_run` (capture not `success`), `below_capture_floor`, `not_gridded`, `grid_stale`, `grid_refused`, ... |
| element key | `host:<id>` (source HOST / DWG / `unrecorded` from `near_face_w_map.host` through `stage_a_sidecar_shapes.model_entry_source`), `link:<inst>:<elem>` |
| px, ink px | `stage_a_kinds._key_sums(arrays, n, "ec_px" / "ec_ink_px")`, the roll-up's reader |
| cells_ink | the key's `ec_` rows with `ec_ink_px >= stage_a_grid.OCCUPANCY_MIN_INK_PX`, through the same `_key_sums` (one `ec_` row per key and cell, `stage_a_grid.merge_sparse`) |
| first_cells | the element's ink cells in its largest measured view; ties go to the lowest view id |
| model_cells_occupancy | grid record `occupancy.all_cells` `model_only + overlap`, summed over measured views |
| created / gone | §2 of the tool docstring: a failed or ungridded view on the other side makes `unmeasured`, never `created` or `gone` |
| id stability | `host_id_jaccard_common_views`: the Jaccard overlap of host element ids over the views measured in both adjacent runs |

**Why cells are ink cells (INFERENCE from the grid's rule).** The grid's
model occupancy is ink, not fill (`stage_a_grid.occupancy`). Counting an
element's cells by the same rule makes them add up the same way as the
per-view figure. In the fixture, the element's 10 ink cells equal the
view's `model_only + overlap` (test
`test_cells_are_the_grids_ink_rule_where_a_row_count_disagrees`). A count of
`ec_` rows would give 12 there: the interior cells hold fill and no ink.

**Why the first appearance is the largest view, not the first requested
(INFERENCE).** Request order is the order the views were enumerated. Adding
views changes it, which would move the figure with no modeling change. The
largest view does not depend on order.

**What `gone` means.** An element that was drawn in run N-1 and is not
drawn, in run N, in any of the views that drew it. Those views must also
have been measured in N (OBSERVED, the rule). That the element was deleted
from the model is INFERENCE: it may have been hidden in those views. The
series CSV keeps `reappearances` so a hidden-then-shown element shows up as
a gap, not as a deletion followed by a creation.

**Bounding the BI figure (absence).** The repository holds no definition of
"Load Cells": a search of every `.md`, `.py`, `.json` and `.csv` for "load
cells", "LoadCells" and "load_cells" returned nothing (OBSERVED). The census
compares against `model_cells_occupancy` because that is what the grid
writes per view. Matching it to the dashboard measure is INFERENCE until
the dashboard's formula is read.

**The dashboard's formulas** (given by Greg, 2026-10-15):

    Load Cells = SUM ( ViewGrid[occupied_cells] )
    Doc Burden = AVERAGEX ( FILTER ( ViewGrid, [is_on_sheet] && NOT ISBLANK ( [density] ) ),
                            [density] )
    Doc Burden Paper Weighted = DIVIDE ( SUMX ( pop, [occupied_cells] ),
                                         SUMX ( pop, [crop_a_cells_with_px] ) )   -- pop: the same filter

`ViewGrid` is built outside this repository: no tool here writes
`occupied_cells` or `density` (OBSERVED, a search of `tools/` and
`vop_interwoven/`). That it is one row per roll-up row, `occupied_cells`
the view's model-or-annotation cells (`model_only + anno_only + overlap`,
overlap once per view), and `density = occupied_cells /
crop_a_cells_with_px` is INFERENCE: the screenshot's Load (about 2.35 M on
11-01) sits below model + annotation (2.49 M), and the paper-weighted ratio
is the size-weighted form of that density. What follows from the formulas
themselves:

- **Load Cells is the drawn series by construction.** It sums cells per
  view, so an element counts once per view it is drawn in, and a view with
  no grid (failed capture, below the floor) has a blank `occupied_cells`
  that `SUM` skips: it counts as 0. That is the 09-13 drop and the 11-01
  jump (§0), which the dashboard's own change panel shows as
  `kept_lost_measure` and `kept_gained_measure`.
- **Doc Burden does not move with the number of views, but it moves with
  the mix.** Both versions are ratios over on-sheet views. The plain one
  averages views equally, so adding sparse sheets pulls it down. The
  paper-weighted one is weighted by view size, so it is pulled by the big
  views. The July drop is in both (by eye, 0.39 -> 0.33 and 0.37 -> 0.29),
  on runs carrying code-change markers. Whether it is the view mix, the
  code change or the model needs a per-view split: views on sheets in both
  runs (density change) against views added or removed (mix). The roll-up
  CSVs of the runs on either side carry the inputs; the census does not.

## 2. The two normalizations, from the identity alone

For one run, with N distinct host-document elements:

    element_cells_ink = first_cells + repeat_cells      (per element, then summed)
    cells_per_element = element_cells_ink / N

Take a run, add a view that draws only elements it already draws, at no
larger size, and re-census. Then:

| figure | change |
|---|---|
| `elements_distinct` | unchanged |
| `first_cells` | unchanged (each element's largest view is still as large) |
| `repeat_cells` | + the new view's element cells |
| `cells_per_element` | + that / N: **rises** |
| `model_cells_occupancy` | + the new view's model cells: **rises** |

That is arithmetic, not a measurement. Two limits on `first_cells` are
INFERENCE and should be checked against the series:

- **Scale.** Cells are paper cells (1/8 in), so an enlarged plan draws an
  element bigger than the overall plan does. A new enlarged-plan set
  therefore raises `first_cells` for the elements it enlarges, even with no
  modeling. To size how much, compare `first_cells` with and without views
  at a scale finer than the series' main plan scale. `views_core`
  carries `Scale`.
- **Membership.** `elements_distinct` counts elements that are VISIBLE in
  at least one measured view. An element modeled but shown in no exported
  view is not counted, and a view-template change that hides a category
  shows up as `gone`. The transition counts by source (`*_LINK`) and the
  per-category counts in the summary are where to look.

So: **`elements_distinct` for "how much was modeled", `first_cells` for
"how big", `created` / `gone` per run for "what changed"**. Keep
`model_cells_occupancy` or `repeat_cells` as the "how much is drawn" series.
`cells_per_element` mixes the two and is better left off the chart.

## 8. How BI builds the series (census 2.0.0, 2026-10-19)

The census is now incremental (`tools/stage_a_element_census.py` 2.0.0,
`tools/README.md`). Each run carries its own census and its transitions
against its predecessor, in its grid folder; `element_census_series.csv`
stays only as the `--out` convenience. The series is built in BI from the
per-run and per-pair files, read through the runs index.

**Which files.** `tools/stage_a_runs_index.py` (1.3.0) gives each run
`census_state` / `census_csv_path_rel` and `transitions_state` /
`transitions_csv_path_rel`. Load a CSV only where its state is `value`; the
path is left empty otherwise, including when the CSV is not the one its
summary names (`csv_mismatch`) (OBSERVED, `census_facts` and
`test_the_runs_index_names_each_runs_census_and_transitions`). A
`no_predecessor` transitions row is the first run of its model folder, with
no CSV: not zero transitions.

**Keys.** Element ids are per model, so the BI key is
`model_key & "|" & element_key` (the index's `model_key`, added to every
row in Power Query), never `element_key` alone (OBSERVED: `host:<id>` is a
host-document ElementId, module docstring "ELEMENT KEYS"; the 1.3.0
`doc_title` column was added for the same reason).

**Tables.**

- `Runs`: `runs_index.csv`, `as_of_date` typed as a date.
- `Census`: the union of every `census_csv_path_rel` file, plus
  `model_key`. One row per element per run.
- `Transitions`: the union of every `transitions_csv_path_rel` file, plus
  `model_key`. One row per element key on either side of a pair, dated by
  the LATER run (`as_of_date`; the predecessor's is `prev_as_of_date`).

**Measures and columns (DAX).**

```DAX
-- Census, calculated column
ElementUID = Census[model_key] & "|" & Census[element_key]

-- Transitions, calculated column
ElementUID = Transitions[model_key] & "|" & Transitions[element_key]

-- Elements: one row per element of the series
Elements =
    ADDCOLUMNS (
        SUMMARIZE ( Census, Census[ElementUID], Census[model_key], Census[element_key] ),
        "First Seen", CALCULATE ( MIN ( Census[as_of_date] ) ),
        "Last Seen",  CALCULATE ( MAX ( Census[as_of_date] ) ),
        "Runs Seen",  CALCULATE ( COUNTROWS ( Census ) )
    )

-- Elements, calculated column: how it entered (the class in its first pair)
Enter How =
    VAR mk = Elements[model_key]
    VAR f = Elements[First Seen]
    VAR seriesStart =
        MINX ( FILTER ( ALL ( Runs ), Runs[model_key] = mk && Runs[census_state] = "value" ),
               Runs[as_of_date] )
    VAR cls =
        LOOKUPVALUE ( Transitions[class],
                      Transitions[ElementUID], Elements[ElementUID],
                      Transitions[as_of_date], f )
    RETURN
        IF ( f = seriesStart, "series_start",
             IF ( cls = "unmeasured_in", "unmeasured", cls ) )

-- Elements, calculated column: how it left (the class in the pair after it was last seen)
Leave How =
    VAR mk = Elements[model_key]
    VAR l = Elements[Last Seen]
    VAR nextRun =
        MINX ( FILTER ( ALL ( Runs ), Runs[model_key] = mk && Runs[census_state] = "value"
                                      && Runs[as_of_date] > l ),
               Runs[as_of_date] )
    VAR cls =
        LOOKUPVALUE ( Transitions[class],
                      Transitions[ElementUID], Elements[ElementUID],
                      Transitions[as_of_date], nextRun )
    RETURN
        IF ( ISBLANK ( nextRun ), "series_end",
             IF ( cls = "unmeasured_out", "unmeasured", cls ) )

-- Measures, by Transitions[as_of_date] (or a Date table related to it)
Created = CALCULATE ( COUNTROWS ( Transitions ), Transitions[class] = "created" )
Gone    = CALCULATE ( COUNTROWS ( Transitions ), Transitions[class] = "gone" )
Created (host) = CALCULATE ( [Created], Transitions[source] <> "LINK" )
Gone (host)    = CALCULATE ( [Gone],    Transitions[source] <> "LINK" )
Distinct Elements = DISTINCTCOUNT ( Census[ElementUID] )
```

**Evidence.**

- The rules above -- first / last seen = MIN / MAX of `as_of_date` over the
  census rows, enter = the class in the first-seen run's pair (else
  `series_start`), leave = the class in the next run's pair (else
  `series_end`) -- reproduce `element_census_series.csv`'s
  `first_as_of_date`, `last_as_of_date`, `runs_seen`, `first_how` and
  `last_how` for every element when run in Python over the per-run and pair
  FILES (OBSERVED,
  `test_first_last_seen_and_enter_leave_from_the_files_are_the_series_csv`,
  four runs with created, new_view, unmeasured and gone elements).
- That the DAX above computes those same rules in Power BI is INFERENCE: it
  has not been run here, and no Power BI model is in the repository.
- `Created` / `Gone` by date equal the runs CSV's `created` / `gone` columns
  for the same run: the pair summary's `counts` equal `transitions()` on the
  same two runs and the `--out` runs CSV's row (OBSERVED,
  `test_the_pair_steps_classes_are_transitions_on_the_same_two_runs`). A
  measure filtered to `source <> "LINK"` is the plain columns, LINK the
  `_LINK` ones.
- Two figures of the series CSV are NOT rebuilt by these rules:
  `runs_unmeasured_between` and `reappearances`. Both need, per element,
  every run between its first and last sighting; the census rows give the
  sightings and the transitions rows the `unmeasured_*` runs, so they are
  computable, but no rule for them is given or tested here (INFERENCE).
- A refused run (none in this series, §0) differs: the `--out` series pairs
  across it with the next run that is not refused; the pair step refuses the
  pairs on both sides of it by name (OBSERVED,
  `test_a_refused_census_refuses_the_pairs_beside_it_and_stays_fresh`), so
  BI shows no transitions there rather than ones measured over two intervals.

**Re-running after a new capture.** `stage_a_analyze.py <new run>
--index-root <Exports>` writes its census, then runs the driver over the
run's model folder, which finds every other run fresh and computes one pair,
then rebuilds the runs index (OBSERVED,
`test_a_new_run_gets_its_pair_against_the_run_analysed_before_it`,
`test_index_root_rebuilds_the_runs_index_with_the_census`). A
recapture of a middle run recomputes that run's census and the two pairs
around it; a backfilled date recomputes the new run's census and pair and the
pair after it (OBSERVED, the `tests/test_stage_a_element_census_incremental.py`
cases of those names).

## 9. Amendment 2026-10-20: replace-in-place moves into the pair step (census 2.1.0)

This section amends §6.3 ("Position, to split churn from creation") and §8
("How BI builds the series"); both stand as written, as the record of what
was decided then.

**What changed.** The replace-in-place pairing that the Power BI
summarizer computed in Power Query is computed by the census pair step
(`tools/stage_a_element_census.py` 2.1.0, `replace_pairs`). It is a function
of the two runs' census CSVs alone, which `pair_identity` already hashes, so
it is fixed per pair. The transitions CSV appends `replaced` and
`replaced_with`; the pair summary's `counts` and the `--out` runs CSV append
`created_replaced`, `created_new`, `gone_replaced`, `gone_removed` and their
`_LINK` splits (OBSERVED, the module and
`tests/test_stage_a_element_census_replace.py`).

**The rule, as BI applied it, reproduced and not improved.** `gone` and
`created` rows only; key = `category` + bbox extent + bbox centre exactly as
the census writes them (1e-6 ft), no tolerance; no bbox value or no
category is never paired; one-to-one, min(n_gone, n_created) per key, each
side in `sorted()` order of `element_key`. That this is exactly what the
Power Query steps did is the brief's statement of them; the Power BI model
is not in the repository, so the equivalence is INFERENCE until BI's
`Replace Pairing Residual` reads 0 against the new column.

**Versions.** Only the pair outputs changed. Census output version 2.0.0 and
pair output version 2.1.0 are now recorded separately (`census_version`,
`pair_version`), so the driver recomputes every pair of this series and none
of its 44 censuses (OBSERVED on a fixture tree written by the 2.0.0 code:
both census summaries' sha256 unchanged, both censuses `fresh`, both pairs
`computed` with reason `pair_version 2.0.0`).

**What to expect on this series (INFERENCE; not run here, the data is not
in the repository).** Exact position is a stricter key than §6.2's category
+ extent, so a week's `created_replaced` should be at most §6.2's matched
count (30-50 % of the smaller side in most weeks, itself an upper bound),
and §6.2 matched on key-set differences rather than the census's own
created / gone, so the comparison is approximate. 06-21 (6 matched) and
03-22 (1) should stay near 0. The 3-day pairs (04-29: 53 created / 41 gone;
09-02: 71 / 63) should show little to pair. If a week's exact match is far
below its extent-only match, that is evidence for a tolerance (centres that
differ by rounding or by a small move); none has been measured, and the
match stays exact until one is.

**Linked elements.** They are under the same rule; `source` is not in the
key. A link element's `bbox_3d` is host-space: the proxy's bbox is built
from the link transform at collection, then its corners go through the same
`bbox_world_aabb` as a host element's (OBSERVED, comments in
`vop_interwoven/color_id_buffer._collect_near_face_w_data`; not checked in
Revit here). So host and link boxes are in one frame and an exact match is
meaningful across them. Three consequences, reported, not changed:
(1) under a rotated link the AABB is inflated as a rotated host element's
is, so two different shapes can share a box -- the same false-positive
limit for both sources; (2) a link re-inserted under a new instance id makes
every linked element `gone` + `created`, and they pair as replaced if the
link is placed exactly where it was, not if it moved; (3) a LINK element can
pair with a host one, and each is counted under its own source, so the
per-split `created_replaced == gone_replaced` holds only when no pair
crosses LINK / not-LINK (the total always holds; the crossings are recorded
as `replace_pairing.cross_source_pairs`). This series has no LINK elements
(§0), so none of the three is exercised by it.

**BI after the merge.** The Transitions query reads `replaced` and drops its
own pairing steps; `New` / `Replaced` / `Removed` keep their definitions;
`Replace Pairing Residual` stays as the check. `reappearances` is not a pair
figure (it needs every run of the series) and stays in BI and the `--out`
series CSV.

## 10. Amendment 2026-10-21: the driver's scope, and pairs keyed on census content (census 2.1.1)

This section amends §9 ("Versions") and the pair step's staleness rule; both
stand as written, as the record of what was decided then.

**What was seen** (Greg's runs, `KSRF/Hosp_Interior_AR`, 47 runs, OBSERVED
from timestamped logs): `census --root` spent 2-3 min judging fresh
censuses; it wrote a refused census and pair into a run still being captured
(11-22, `finalized: false`) and value censuses of every-view-`not_gridded`
into two runs never gridded (11-08, 11-15); and re-analysing 10-25 from the
same captures recomputed the 10-25 and 11-01 pairs every time.

**Scope.** The `--root` driver now skips, before anything is written for it,
a run whose run_meta is absent, unreadable or not finalized, and a run none of
whose model sidecars has a `<stem>.grid.json` in its grid folder. Nothing is
written into a skipped run and no folder is made. A skipped run is not in the
series: the next run pairs with the latest earlier run in scope, and its pair
records which. Files already in a skipped run (the 11-22 summaries) are left
and named; deleting them is Greg's decision. A skip is not a refusal.

**Why the pairs went stale** (INFERENCE from the code; not yet checked against
Greg's files): `stage_a_analyze` step 6 rewrites the named run's census every
time, and a census summary records its inputs' sha256 and the TIFFs'
`[size, mtime_ns]`. The register step rewrites every registration record with
a new `elapsed_ms` (wall time), which changes the record's sha256 and, through
`registered_annotation.record_sha256`, the grid json's. So the summary's bytes
changed and the 2.1.0 pair identity -- the sha256 of the whole summary --
changed with them, over an unchanged census CSV. The grid npz is not a cause
on CPython 3.6+: `zipfile.ZipFile.open(name, "w")` dates the member
1980-01-01, not now (OBSERVED in the 3.13 source here; a re-grid under a clock
moved a year writes byte-identical npz and grid json,
`tests/test_stage_a_element_census_scope.py`).

**Pair identity (2.1.1).** A pair is a function of what it reads of each
census: the CSV (its recorded sha256) and the summary fields `PAIR_READS`
(schema, census version, state, refusal, run_id, as-of date, measured and
unmeasured view ids, CSV name and sha256). The identity is those two hashes
per side. `PAIR_VERSION` 2.1.1 recomputes every pair once; no census is
recomputed and no census summary changes.

**Not changed, and why.** A re-registered run's census still goes stale
(`elapsed_ms`); it is the named run, which step 6 recomputes anyway, and its
pairs now stay fresh. Removing `elapsed_ms` from the persisted registration
record would change `register_stage_a_annotation` and is Greg's decision.
